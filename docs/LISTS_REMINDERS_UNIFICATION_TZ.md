# Lists And Reminders Unification TZ

Документ описывает ТЗ на объединение пользовательского опыта списков и напоминаний. Цель - убрать дублирование разделов, но не сломать текущие сценарии списков, checklist-run, shared lists, лекарств и водительских напоминаний.

## Референсы

- Todoist: reminders are attached to tasks; date/time on a task can create automatic reminders, custom reminders can be relative to due date, recurring reminders are supported. Source: https://get.todoist.help/hc/en-us/articles/205348301-Introduction-to-reminders
- Microsoft To Do: the product model is list -> task; tasks support due dates and reminders. Source: https://support.microsoft.com/en-gb/office/welcome-to-microsoft-to-do-762cbbf9-7fc1-48e5-b619-005622da89d0
- TickTick: tasks live in regular/smart lists; calendar and smart lists are views over tasks with dates/reminders. Source: https://help.ticktick.com/articles/7055782283059396608
- Google Keep: notes and lists can be shared and can have reminders. Source: https://support.google.com/keep/answer/2888240

## Текущая Модель Проекта

- `TodoList` - контейнер пользовательских списков.
- `ListItem` - пункт списка с `text`, `is_completed`, `position`.
- `ChecklistRun` - персональный snapshot прохождения списка.
- `Reminder` - отдельная сущность с `text`, `title`, `remind_at_utc`, `repeat_rule`, `status`, `source_module`.
- `Reminder.list_id` уже позволяет привязать напоминание к списку, но не к конкретному пункту списка.
- `/me/reminders` показывает `source_module in ["general", "list"]`.

## Продуктовое Решение

Не объединять таблицы физически в первом шаге. Объединить пользовательскую модель:

- `Списки` становятся основным разделом для задач, чек-листов и напоминаний.
- `Напоминания` становятся smart-view: "Сегодня", "Предстоящие", "Просроченные", "Без списка".
- Напоминание больше не воспринимается как отдельный тип контента, а как дата/сигнал у задачи, пункта списка или списка.
- Отдельные домены `Лекарства` и `Водитель` остаются отдельными: их напоминания не смешивать в обычные списки, но можно показывать в общей сводке "Сегодня".

Причина: это соответствует паттернам Todoist/Microsoft To Do/TickTick и минимизирует риск миграции. Полное слияние `ListItem` и `Reminder` сейчас приведет к сложной миграции shared-list ролей, checklist snapshots и worker-логики.

## MVP

### Навигация

- В Telegram и Mini App оставить один основной раздел `Списки`.
- Внутри `Списки` добавить быстрые фильтры:
  - `Все`;
  - `Сегодня`;
  - `Предстоящие`;
  - `Просроченные`;
  - `Без даты`;
  - `Выполненные`.
- Раздел `Напоминания` переименовать в `Сегодня` или `Сроки` и сделать smart-view, а не отдельной CRUD-зоной.
- На переходном этапе не удалять старую callback/API-совместимость `reminders_*`, чтобы не сломать старые сообщения и тесты.

### Списки

- В карточке списка показывать связанные напоминания списка.
- Для списка добавить действие `Напомнить о списке`.
- Для пункта списка добавить действие `Напомнить о пункте`.
- У пункта списка в UI показывать:
  - текст;
  - статус выполнения;
  - дату/время напоминания, если есть;
  - повтор, если есть.

### Напоминания

- Создание напоминания без списка должно создавать "задачу без списка" в системном списке `Входящие` или оставаться `Reminder(source_module="general")` на первом этапе.
- Создание напоминания из списка должно привязывать его к списку и, после миграции, к конкретному пункту.
- Выполнение напоминания, связанного с пунктом, должно предлагать отметить пункт выполненным.
- Отмена напоминания не должна удалять пункт списка.
- Удаление пункта списка должно отменять или отвязывать активные напоминания этого пункта.

## Data Model

### Этап 1 - Без Миграции

Использовать существующее поле `Reminder.list_id`.

Ограничения этапа:

- напоминание можно привязать к списку, но не к конкретному пункту;
- в UI напоминание показывается внутри списка как связанное со списком;
- быстрый сценарий `Напомнить о пункте` создает reminder с текстом пункта и `list_id`, но без жесткой FK-связи с `ListItem`.

### Этап 2 - Связь С Пунктом

Добавить миграцию:

```text
reminders.list_item_id nullable FK -> list_items.id ON DELETE SET NULL
index ix_reminders_list_item_status(list_item_id, status)
```

Правила:

- `Reminder.list_id` остается для напоминаний всего списка.
- `Reminder.list_item_id` используется для напоминаний конкретного пункта.
- Если `list_item_id` задан, backend проверяет доступ к родительскому списку.
- При удалении списка reminder отменяется каскадом через бизнес-логику или теряет `list_id/list_item_id` по FK, в зависимости от выбранной политики миграции.

## API

### Новые Или Расширенные Поля

- `ListItemResponse.reminder_count`
- `ListItemResponse.next_reminder_at_utc`
- `ListItemResponse.repeat_rule`
- `ReminderSummaryResponse.list_item_id`
- `ReminderCreateRequest.list_item_id`
- `ReminderUpdateRequest.list_item_id`

### Новые Endpoints

```text
POST /me/lists/items/{item_id}/reminders
GET  /me/lists/items/{item_id}/reminders
POST /me/lists/{list_id}/reminders
GET  /me/tasks/today
GET  /me/tasks/upcoming
GET  /me/tasks/overdue
```

Для MVP можно реализовать новые endpoints поверх `ReminderService`, без удаления `/me/reminders`.

## Telegram UX

### Создание

- `Списки -> список -> пункт -> Напомнить`
- быстрые варианты: сегодня, завтра, через неделю, выбрать дату, без повтора, каждый день, каждую неделю, каждый месяц.
- после создания: "Напоминание добавлено к пункту: ...".

### Уведомление

Для напоминания пункта:

```text
⏰ Напоминание
Список: Покупки
Пункт: Купить молоко

[✅ Выполнено] [⏰ Отложить] [📋 Открыть список]
```

Для напоминания списка:

```text
⏰ Напоминание о списке
Покупки

[📋 Открыть список] [✅ Закрыть] [⏰ Отложить]
```

## Mini App UX

- В списке пунктов добавить компактный индикатор даты/напоминания.
- В форме пункта добавить блок `Дата и напоминание`.
- Раздел `Сегодня` показывает единый список:
  - пункты списков с датой;
  - общие напоминания;
  - активные checklist-runs;
  - опционально лекарства/водительские события отдельными группами.
- Не показывать admin UI в этом flow.

## Permissions

- `owner` и `editor` общего списка могут создавать и менять напоминания к пунктам.
- `viewer` может видеть напоминания списка, но не может менять их.
- Личные напоминания участника общего списка требуют отдельного решения:
  - MVP: напоминание на общий пункт создается только для текущего пользователя;
  - после MVP: owner/editor может назначать reminder другим участникам.

## Worker Logic

- Worker продолжает выбирать `Reminder.status == ACTIVE` и `remind_at_utc <= now`.
- Notification payload должен учитывать `list_id` и `list_item_id`.
- Для повторов:
  - если пункт выполнен, следующий повтор не создается без подтверждения;
  - если повтор активен, выполнение одного reminder не должно автоматически отмечать весь список.

## Migration Plan

1. Этап 1: UX-unification без схемы.
2. Этап 2: добавить `list_item_id` в `Reminder`.
3. Этап 3: добавить UI для напоминаний на пункт.
4. Этап 4: перевести раздел `Напоминания` в smart-view.
5. Этап 5: убрать дублирующие старые кнопки после периода совместимости.

## Acceptance Criteria

- Пользователь может создать напоминание из списка.
- Пользователь может создать напоминание из пункта списка.
- Напоминание видно и в списке, и в smart-view `Сегодня/Предстоящие`.
- Web/Mini App и Telegram показывают одинаковую логику статусов.
- Старые `/me/reminders` и callback-сценарии продолжают работать.
- Shared-list права соблюдаются.
- Checklist-run snapshot не меняет исходный список и не ломает напоминания.
- Тесты покрывают personal list, shared list owner/editor/viewer, reminder done/cancel/delete, overdue/upcoming views.

## Не Входит В MVP

- Назначение напоминаний другим участникам общего списка.
- Location-based reminders.
- Несколько напоминаний на один пункт.
- Календарная сетка месяц/неделя.
- Полное удаление раздела `/me/reminders`.
